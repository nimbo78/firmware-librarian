# Пространства знаний: архитектура и план

Статус: **фаза 1 сделана** (09.2026), решения владельца внесены. Документ —
решения и их обоснования; по мере реализации переезжает в CLAUDE.md
как инварианты.

## Зачем

Сейчас бот — про один продукт: один набор чатов-источников, один системный
промпт («инженеров по оборудованию Huawei»), глобальный поиск по всему
корпусу. Владелец хочет подключать чаты по другим продуктам (B4, Telemt, …)
и **решать любой вопрос в одном боте**, при желании сужая поиск до одной
области указателем в тексте вопроса.

Без изменений подключение чужого чата даёт не мультипродуктовость, а
перемешивание: вопрос про WLAN из Huawei-чата притащит фрагменты про
беспроводку MikroTik, промпт назовёт бота «ассистентом по Huawei» в чате
про B4, а каталог `/fw` попытается разобрать имена файлов, к которым его
регулярки не имеют отношения.

## Ключевые решения

### 1. Пространство — свойство чанка, одна база

**Пространство** (space) — область знаний: набор чатов-источников, папка с
документами, персона в промпте, подсказки терминологии, чаты, где бот
отвечает. У каждого чанка ровно одно пространство происхождения; у вопроса —
область поиска (одно пространство или все).

Хранение: колонка `chunks.space` в **той же базе**. Отвергнутая альтернатива —
отдельный файл SQLite на пространство с фасадом поверх — провалила «тест на
удаление»: фасад стал бы пробросом для десятка методов, а `state`, `files`,
`qa_log`, `events` пришлось бы либо дублировать, либо назначать «домашнюю»
базу. Глобальный поиск (основной сценарий владельца) в одной базе — это один
ранжированный список, а не слияние N результатов.

### 2. Скорость: partition key в sqlite-vec

Проверено на `sqlite-vec v0.1.9`: `vec0(space TEXT PARTITION KEY, embedding
float[1024])` даёт KNN внутри раздела со сканом только его строк — при трёх
пространствах в 2.6 раза быстрее полного, а глобальный поиск не меняется.
FTS5 получает колонку `space UNINDEXED` и фильтр в том же запросе.

Следствие: поиск по своему пространству остаётся ~0.6 с сколько бы чатов ни
подключили; глобальный растёт линейно с корпусом.

### 3. Область поиска по умолчанию: своё пространство, потом все

Вопрос из чата, привязанного к пространству, ищется сначала в нём. Пусто —
автоматический повтор по всем пространствам с пометкой «в вашей области не
нашлось, вот из соседних». Чат без привязки (личка админа, общий чат) —
сразу глобально. Указатель в тексте переопределяет: `#b4 вопрос` — только
B4, `#all вопрос` — всё.

Почему не глобально по умолчанию: «WLAN на Huawei» и «WLAN на MikroTik» —
разные ответы, и смешивать их без явной просьбы хуже, чем промолчать.
Регулируется в конфиге (`default_scope = "home" | "all"`).

Синтаксис указателя — хэштег `#b4` (решение владельца): Telegram его
подсвечивает, пользователи знают. `/ask@b4` не годится — так Telegram
адресует команды конкретному боту. Указатель работает и в группе, и в личке
админа — в личке это единственный способ выбрать область.

Когда ответ пришёл не из своего пространства (сработал fallback) или область
задана указателем, бот пишет об этом строкой в ответе — иначе непонятно,
откуда знание (решение владельца).

### 4. Промпт и расширение запроса — из конфига пространства

Персона (`persona`) и подсказки терминологии для расширения запроса (`hints`)
живут в конфиге пространства. В глобальном режиме персона общая, а каждый
фрагмент контекста помечен пространством — `[3] (b4 · топик «Обход»)`, —
чтобы модель понимала, к какой области относится ответ, и говорила об этом.

### 5. Каталог остаётся плагином Huawei (B4 и Telemt — только знания)

Парсер имён прошивок и `/fw` включаются только в пространствах с
`catalog = "huawei"`. Файлы других пространств каталогизируются (таблица
`files`), но связки прошивок для них не строятся — иначе регулярки дадут
ложные совпадения на случайных именах. Парсер под другого вендора
(RouterOS `.npk`) — отдельный плагин, когда понадобится. Для B4 и Telemt
прошивок нет вообще: у них нет ни `folder`, ни `download` — только чаты
как источник знаний (решение владельца).

### 6. Конфигурация — `spaces.toml`, env остаётся как «одно неявное пространство»

Python 3.11+ читает TOML без зависимостей (`tomllib`). Файл лежит рядом с
`.env` и монтируется в оба контейнера. **Если файла нет — из существующих
`KB_CHAT_IDS`/`KB_ANSWER_CHAT_IDS`/`DOWNLOAD_FOLDER` собирается одно неявное
пространство, и поведение не меняется.** Это гарантия обратной
совместимости: фаза 1 деплоится без единого изменения в `.env`.

```toml
[huawei]
title      = "Huawei"
persona    = "инженеров по оборудованию Huawei"
hints      = "терминология Huawei: VRP, CloudEngine, AirEngine, HedEx, версии V200R0xx"
chats      = [-100HHHHHHHHHH]          # источники знаний (бывший KB_CHAT_IDS)
answer     = ["-100HHHHHHHHHH:15"]     # где отвечает; формат как у KB_ANSWER_CHAT_IDS
folder     = "/app/downloads"          # документы и прошивки этого пространства
catalog    = "huawei"                  # парсер имён и /fw; "none" — выключено
download   = { chats = [-100HHHHHHHHHH], extensions = ["pdf", "hdx", "zip"] }
gaps_chat  = -100HHHHHHHHHH
gaps_topic = 0
default_scope = "home"

[b4]
title      = "B4 и обход блокировок"
persona    = "администраторов B4, mihomo и MikroTik"
hints      = "mihomo, sing-box, RouterOS, WireGuard, DPI, Xray"
chats      = [-100XXXXXXXXXX]
answer     = ["-100XXXXXXXXXX"]
folder     = "/app/downloads-b4"
catalog    = "none"
```

## Что меняется в коде

| Модуль | Изменение |
|---|---|
| `kb_spaces.py` (новый) | `Space`, `load_spaces()` (toml или неявное из env), `space_for_chat()`, `parse_selector()` — единственное место, где текст «#b4 вопрос» превращается в область поиска |
| `kb_store` | `chunks.space`, `files.space`, `qa_log.space`; `chunks_vec` с partition key; `chunks_fts` с `space UNINDEXED`; `search(..., space=None)`; `sources_report` по пространствам |
| `kb_spaces_migrate.py` (новый) | разовая миграция: существующие строки → пространство по умолчанию, пересборка `chunks_vec`/`chunks_fts` (локально, без API) |
| `kb_ingest` | `ingest_chat` пишет `space`; ключи состояния документов получают пространство (`hedex_ingested:<space>:<md5>`) |
| `kb_pipeline` | цикл по пространствам: документные шаги идут по `space.folder` и метят чанки; каталожные — только при `catalog != "none"`; бэкап один |
| `kb_answer` | `answer_question(store, question, dialog, scope)`: персона и подсказки из пространства, метки пространства в контексте при глобальном поиске, авто-fallback |
| `kb_bot` | чаты ответа — из `answer` всех пространств; разбор указателя; gaps-петля по пространствам |
| `librarian` | качалка: чаты, расширения и папка — из `download` пространства; журнал дедупликации живёт в папке, то есть сам по себе становится per-space |
| `kb_render` | `/sources` и `/status` группируют по пространствам |

Ключи состояния `hedex_ingested:<md5>` без пространства (существующие)
трактуются как принадлежащие пространству по умолчанию.

## Память и масштаб

Измерено на проде: 185 тыс. чанков = 2.1 ГБ файла, ~11 КБ на чанк (текст +
вектор + FTS). При 10 ГБ RAM и ~6.5 ГБ доступных база уверенно кэшируется
до ~5 ГБ, то есть **~450 тыс. чанков**. Большой Telegram-чат (300 тыс.
сообщений) даёт ~60 тыс. чанков ≈ 0.7 ГБ — запас примерно на четыре таких
чата сверх текущего. Дальше — бинарная квантизация (схема отработана,
см. CLAUDE.md) или SSD-кэш на NAS.

Стоимость бэкфилла большого чата на DeepInfra — порядка $0.10 эмбеддингов;
время — часы итерации по истории через Telethon. Vision/whisper включаются
флагами отдельно и в конфиге пространства могут быть выключены.

## Фазы

**Фаза 1 — модель пространств, поведение не меняется** ✅ сделано
`kb_spaces.py` (конфиг, `Space`/`Spaces`, разбор указателя) + селфтест;
`chunks.space`/`files.space`/`qa_log.space`; `chunks_vec` с partition key,
`chunks_fts` с колонкой `space`; `search(..., space=None)`;
`kb_spaces_migrate.py` + селфтест на синтетической базе старой схемы и
прогон на копии прода. Без `spaces.toml` всё работает как раньше: одно
неявное пространство из env. Хранилище отказывается открывать
немигрированную базу с данными — иначе поиск по пространству молча стал бы
глобальным.

**Фаза 2 — поиск и ответ по пространствам** (~1 день)
Указатель `#slug`/`#all`, персона и подсказки из конфига, метки в контексте,
авто-fallback, `/sources` и `/status` по пространствам, gaps-петля на
пространство. Проверяется через `kb_bot_check` и селфтесты `kb_answer`/
`kb_render`.

**Фаза 3 — мульти-инжест** (~1 день)
Цикл инжеста по `space.chats`; качалка и документные конвейеры по папкам
пространств с метками; `kb_backfill --space b4`.

**Фаза 4 — первое новое пространство** (полдня + время бэкфилла)
`spaces.toml` с B4, том под папку, `--dry-run`, бэкфилл, замер RAM и
задержек поиска, подстройка `default_scope`.

**Фаза 5 — по потребности**
Плагин каталога под RouterOS; квантизация при базе >5 ГБ.

## Риски

- **Окно миграции.** Замерено на копии прода (6617 чанков, 1024 измерения):
  22 с, векторы побайтово те же, выдача поиска совпала. Прод — 185 тыс.
  чанков (~760 МБ векторов), то есть порядка 10–30 минут на дисках NAS плюс
  бэкап. Нужно ~3 ГБ свободного места: копия `.pre-spaces` весит как база,
  а файл временно растёт (старая векторная таблица освобождается, но SQLite
  не отдаёт место обратно — оно переиспользуется дальнейшими вставками).
  Скрипт идемпотентен, повторный запуск ничего не делает.
- **Качество ответов в глобальном режиме.** Смешение областей — риск
  путаницы; поэтому по умолчанию своё пространство, а глобально — с метками
  и явной оговоркой модели.
- **Два источника правды в конфиге.** Если есть `spaces.toml`, переменные
  `KB_CHAT_IDS`/`KB_ANSWER_CHAT_IDS` игнорируются с предупреждением при старте.
- **Один документ в двух пространствах.** Ключи состояния документов
  включают пространство — иначе второе пространство сочтёт файл обработанным.

## Решения владельца и что осталось

1. ✅ Указатель — `#b4` (и `#all`).
2. ✅ Область по умолчанию — своё пространство чата с авто-fallback, о
   переходе к соседним областям бот сообщает в ответе.
3. ✅ B4 и Telemt — только знания: ни скачивания, ни каталога.
4. ✅ Папки документов новых пространств — отдельные тома в compose.
4. Id чатов-источников и чатов ответа для новых пространств — владелец
   даст к фазе 4. Обычно это одни и те же чаты: если в `[space]` задан
   только `chats`, бот отвечает во всех них целиком (`answer` не нужен).
