# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Назначение

Проект **firmware-librarian** (бывший telegram-file-downloader; compose-проект зафиксирован `name:` в docker-compose.yml). Два сервиса в одном docker-compose на NAS Synology DS720+:

1. **Качалка** ([librarian.py](librarian.py)) — Telethon user-клиент, слушает чаты `CHAT_IDS`, скачивает документы с подходящим расширением, дедуплицирует по имени + MD5, складывает на том NAS. Плюс ночной инжест базы знаний (см. ниже).
2. **KB-бот** ([kb_bot.py](kb_bot.py) — клиент и обработчики; поиск и сборка ответа в [kb_answer.py](kb_answer.py), вёрстка каталога и навигация в [kb_render.py](kb_render.py): оба импортируются БЕЗ переменных окружения Telegram и принимают хранилище параметром, поэтому покрыты селфтестами) — бот (токен BotFather), отвечает на `/ask` и `@упоминание` в чатах `KB_ANSWER_CHAT_IDS`, используя RAG по истории чатов: гибридный поиск sqlite-vec + FTS5, ответы через OpenAI API.

## Команды

- Локальный запуск качалки: `pip install -r requirements.txt` затем `python librarian.py`. При отсутствии валидного `bot.session` Telethon запросит номер телефона в интерактиве — поэтому первый запуск делается с tty.
- Docker: `docker compose up --build` (Compose V2 — без дефиса). Переменные окружения подтягиваются из `.env` рядом с `docker-compose.yml`.
- Передеплой на NAS: [`./redeploy.sh`](redeploy.sh) — проверяет наличие `.env` и `bot.session`, делает `down --remove-orphans` + `up --build -d` + выводит статус и последние 30 строк логов.
- Selftest хранилища (не требует Telegram и OpenAI): `pip install sqlite-vec && python kb_store.py`.
- Миграция базы под области знаний (разово, при остановленных сервисах): `touch spaces.toml` (**обязательно ДО любой compose-команды**: том `./spaces.toml` монтируется в оба сервиса, а bind-mount несуществующего файла падает — `Bind mount failed: ... does not exist`; `redeploy.sh` создаёт файл сам, но миграция идёт раньше него) → `docker compose stop librarian kb-bot` → `docker compose run --rm librarian python kb_spaces_migrate.py` → `docker compose start librarian kb-bot`.
- Бэкфилл истории в базу знаний — см. процедуру в разделе «База знаний».
- Отладочный поиск по базе: `docker compose run --rm librarian python kb_search.py "вопрос"`.
- Локальные конвейеры без Telegram (архивы/HedEx/PDF/экстракция; сессию не трогает, качалку можно не гасить): `docker compose run --rm librarian python kb_backfill.py --local-only`.
- Селфтесты (без Telegram и OpenAI): `python kb_store.py`, `kb_firmware.py`, `kb_render.py`, `kb_hedex.py`, `kb_archive.py`. Мультипространственный режим — `python kb_spaces_check.py`, конфиг областей — `kb_spaces.py`, миграция схемы — `python kb_spaces_migrate.py --selftest`. Групповые команды бота — `python kb_bot_check.py` (отдельный файл: kb_bot на импорте читает env и открывает базу, поэтому окружение задаётся ДО импорта; подменяет event и прогоняет обработчики без сети, а `FakeEvent.fail` заставляет Telegram «отказать» — так проверяется тихая обработка закрытого топика). Линтеров и CI нет.

## Переменные окружения

Шаблон — [.env.example](.env.example): `cp .env.example .env` и заполнить.

Качалка:

- `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` — обязательны.
- `CHAT_IDS` — обязательна, CSV целых чисел (id чатов, как видит их Telegram, часто отрицательные).
- `FILE_EXTENSIONS` — CSV расширений **без точки**, по умолчанию `pdf,jpg,png`. Регистр и пробелы нормализуются ([librarian.py](librarian.py), `FILE_EXTENSIONS` и фильтр в `handler`).
- `DOWNLOAD_FOLDER` — по умолчанию `./downloads`; в Docker переопределяется на `/app/downloads`.

База знаний (все опциональны — без них KB-подсистема выключена):

- `OPENAI_API_KEY` — эмбеддинги и ответы.
- `KB_CHAT_IDS` — CSV чатов-источников знаний (ночной инжест).
- `KB_BOT_TOKEN`, `KB_ANSWER_CHAT_IDS` — токен BotFather и чаты, где бот отвечает. Формат записи — `<чат>` или `<чат>:<топик>` (несколько топиков — несколько записей); без топика бот отвечает в чате где угодно. `KB_CLEANUP_MINUTES` — через сколько минут убирать служебные сообщения бота в группе (0 = не убирать).
- `TZ` — часовой пояс контейнера; от него зависит `INGEST_HOUR` (по умолчанию 5).
- `KB_VISION`/`KB_VOICE`/`KB_PDF` — флаги обогащения (`1` включает; по умолчанию `0`): картинки через vision, голосовые через Whisper, текстовый слой скачанных PDF.
- `KB_ARCHIVE` — просмотр архивов из папки загрузок (`1` включает; по умолчанию `0`), см. [kb_archive.py](kb_archive.py).
- `KB_WEB` — веб-поиск при ответах бота (`1` включает; по умолчанию `0`).
- `KB_ADMIN_IDS` — CSV telegram user id админов: команды в личке бота (`/status`, `/events`, `/notify on|off`) и уведомления о событиях.
- `KB_GAPS_CHAT_ID`/`KB_GAPS_TOPIC_ID` — куда постить еженедельный список вопросов без ответа (пусто — пост выключен; авто-ответ авторам работает независимо).
- `EMBED_MODEL`/`EMBED_DIM` (`text-embedding-3-small`/512), `ANSWER_MODEL`/`KB_VISION_MODEL` (`gpt-5-mini`), `KB_DB_PATH` (`/app/kb/kb.sqlite`), `KB_BACKEND` (`sqlite`).
- `EMBED_API_BASE`/`EMBED_API_KEY` — сторонний OpenAI-совместимый провайдер ТОЛЬКО для эмбеддингов (рекомендация — DeepInfra + `BAAI/bge-m3`, см. ниже); пусто = эмбеддинги через OpenAI. `EMBED_PRICE_PER_MTOK` — переопределение цены для оценок бюджета, если модель не из встроенной карты `EMBED_PRICES` ([kb_ingest.py](kb_ingest.py)).

## Архитектура и неочевидные детали

- **Качалка — user-клиент Telethon, а не Bot API.** Имя `bot.session` и переменная `client` вводят в заблуждение: [librarian.py](librarian.py), `run()` вызывает `client.start(phone=...)` — аутентификация идёт по телефону пользователя. Бот-токен использует только `kb_bot.py` (отдельная сессия на томе `/app/kb`).
- **`bot.session` НЕ коммитится (в `.gitignore`), но копируется в Docker-образ** ([Dockerfile:14](Dockerfile#L14)). Файл = полный доступ к аккаунту, поэтому в репозиторий не попадает, но обязан присутствовать в каталоге сборки на хосте, где выполняется `docker compose build` (иначе сборка упадёт на `COPY bot.session`, а без сессии контейнер заблокировался бы на интерактивном вводе телефона). Создаётся/пересоздаётся локальным запуском с tty; на новом хосте файл переносится вручную (не через git).
- **Одна Telethon-сессия = один процесс.** Второе подключение с тем же `bot.session` убивает первое (`AuthKeyDuplicatedError`). Поэтому ночной инжест живёт внутри процесса качалки, а `kb_backfill.py` запускается только при остановленной качалке.
- **Состояние дедупликации живёт в томе загрузок.** `downloaded_files.txt` пишется в `DOWNLOAD_FOLDER` ([librarian.py](librarian.py), `downloaded_files_log`); в [docker-compose.yml:27](docker-compose.yml#L27) этот путь смонтирован на NAS `/volume1/public/Repository/Hardware/Huawei/fromChat`. Журнал переживает перезапуски, но привязан к конкретному пути NAS — при смене тома история дедупликации теряется.
- **Формат журнала: `<md5>,<file_name>`** (`save_downloaded_file` в [librarian.py](librarian.py)). MD5 — фиксированные 32 hex-символа, поэтому `partition(',')` корректно отделяет хэш от имени, в котором могут быть запятые. На чтение поддерживается также старый формат `<file_name>,<md5>` (`load_downloaded_files`) — миграция файла на диске не требуется.
- **Дедупликация** (`handler` в [librarian.py](librarian.py)): ключ — имя файла + MD5. При каждом событии перехэшируется уже лежащий локально файл. Если `downloaded_files.txt` потерян, но файлы остались — они скачаются повторно и **затрут** локальные копии. Файлы с тем же именем и новым содержимым обрабатываются как «перезапись», старая версия теряется.
- **Огрызки от обрывов скачивания удаляются.** `download_media` обёрнут в try/except ([librarian.py](librarian.py), `handler`); при `OSError`/`TimeoutError`/`RPCError` частично скачанный файл удаляется, в журнал ничего не пишется.
- **Path traversal невозможен.** Имя из Telegram прогоняется через `os.path.basename` и проверяется на `.`/`..` (`handler` в [librarian.py](librarian.py)) до сборки `file_path`.
- **Обрабатываются только документы** (`handler` в [librarian.py](librarian.py)): `event.message.media` должен иметь атрибут `document`. Фото, отправленные как изображения (не как файл), пропускаются — Telegram кладёт их в `MessageMediaPhoto`. Документы без расширения отсекаются явно (`handler`).

## База знаний (RAG)

- **Хранилище — один файл SQLite** (`/volume1/docker/tg-kb/kb.sqlite`): таблица `chunks` + векторная `chunks_vec` (sqlite-vec) + полнотекстовая `chunks_fts` (FTS5) + `state`. Гибридный поиск: KNN + FTS, слияние через Reciprocal Rank Fusion ([kb_store.py](kb_store.py)).
- **Весь доступ к базе — только через `kb_store.open_store()`.** Это точка будущего переезда на Qdrant (`KB_BACKEND`): новый класс с тем же интерфейсом + переливка чанков с готовыми векторами. Вектора хранятся в базе именно ради миграции без переэмбеддинга; state всегда остаётся в SQLite.
- **rowid-связка таблиц.** `chunks_vec` и `chunks_fts` привязаны к `chunks.rowid`. В `chunks` нельзя писать через `INSERT OR REPLACE` — REPLACE меняет rowid и отвязывает вектор/FTS. `upsert_chunks` ([kb_store.py](kb_store.py)) пишет одним `INSERT ... ON CONFLICT(id) DO UPDATE`: строка правится на месте, rowid сохраняется. Раньше там было «SELECT, потом INSERT или UPDATE» — и это разваливалось при двух писателях: SELECT в python-sqlite3 идёт в автокоммите, ДО начала пишущей транзакции, поэтому сосед (ночной инжест того же чата или второй бэкфилл) успевал вставить тот же id между проверкой и вставкой, и прогон падал на `UNIQUE constraint failed: chunks.id`. Регрессия — в селфтесте `kb_store.py`.
- **ID чанка детерминирован**: `sha1(chat_id:msg_first:msg_last)`. Повторный инжест идемпотентен: переэмбеддится только новое и изменившееся — сравнение по sha1 текста (`ingest_chat` в [kb_ingest.py](kb_ingest.py)).
- **Чанк — это фрагмент беседы**, не сообщение: сообщения топика группируются до паузы >30 минут или ~4000 символов (`build_chunks` в [kb_ingest.py](kb_ingest.py)). Названия топиков форума берутся через `GetForumTopicsRequest`.
- **Медиа-сообщения всегда попадают в чанк** плейсхолдером `[изображение]`/`[голосовое]`, даже при выключенных флагах — границы чанков не зависят от обогащения (иначе включение флага потом сдвинуло бы границы и наплодило дубликатов). Обогащение лишь расширяет плейсхолдер описанием: id чанка тот же, инжест переэмбеддит его по несовпадению sha1 текста (`chunk_hashes`). Полный прогон (`min_id=0`) дополнительно удаляет чанки чата с устаревшими границами (`prune_chunks`).
- **Бэкфилл трёхэтапный**: [1/3] текст (`enrich_media=False` — база отвечает уже после этого этапа), [2/3] vision/whisper в `media_cache` (`enrich_chat_media`), [3/3] пересборка чанков с описаниями (переэмбед только изменённых).
- **Инжест идёт от `last_seen_id`** (state в базе), а не «за сутки»: пропущенные запуски догоняются сами; state двигается только после успешной записи (`ingest_chat`).
- **Битая картинка не ретраится вечно.** Заявленный Telegram mime бывает враньём (`image/png`, а внутри что угодно): vision отвечает `400 invalid_image_format`. Ошибка не тарифицируется, но повторялась бы каждый прогон, поэтому `enrich_message` пережимает картинку через Pillow и пробует ещё раз, а если Pillow тоже не осилил — кэширует пропуск (`''`) навсегда. Прочие сбои провайдера (5xx, таймауты) НЕ кэшируются, как и раньше — они лечатся ретраем.
- **Обогащение медиа — опционально, по умолчанию выключено**: `KB_VISION=1` (картинки через vision: описание + OCR), `KB_VOICE=1` (голосовые через Whisper), `KB_PDF=1` (текстовый слой скачанных PDF, [kb_pdf.py](kb_pdf.py)). Видео сознательно не обрабатываются. Результаты vision/whisper кэшируются в `media_cache` (`enrich_message` в [kb_ingest.py](kb_ingest.py)) — ретраи не платят дважды; ошибки НЕ кэшируются (retry). Не-png/jpeg/gif/webp картинки конвертируются в JPEG через Pillow (vision API другое не принимает); неконвертируемое (HEIC, мусор) кэшируется как пропуск. PDF учитываются по MD5 (state `pdf_ingested:<md5>`).
- **PDF-чанки имеют синтетический положительный `chat_id`** (из MD5 файла) — у Telegram-чатов id отрицательные, поэтому бот показывает «файл, стр. N» вместо ссылки t.me ([kb_pdf.py](kb_pdf.py), [kb_bot.py](kb_bot.py)).
- **Архивы (`KB_ARCHIVE=1`)** — [kb_archive.py](kb_archive.py), три контура на архив (zip/rar/7z/tar/gz): (1) листинг в таблицу `archive_files` (rar листается чистым Python — rarfile парсит заголовки сам, бэкенд `unar` в образе нужен только для извлечения); (2) **каталог по внутренностям** — имена членов через `parse_firmware_name` → связки firmware с `source='archive'`: сборка «для_апгрейда.rar» с `.cc/.pat` внутри находится через /fw, хотя её имя не парсится; (3) текст из pdf/docx/xlsx/txt/html → RAG **потоково в память** (по одному члену, RAM-пик ≤50 МБ; бинарники не читаются; конвенция чанков как у PDF). Исключение: `.hdx` внутри архива извлекается НА ДИСК в `hedex_extracted/` (потоково, лимит 2 ГБ) — шаг архивов в пайплайнах стоит ПЕРЕД шагом HedEx, рекурсивный `list_hdx` подпапку видит. Идемпотентно: state `archive_scanned:<md5>`, md5 — из журнала качалки (для положенных руками — считается). Лимиты против zip-бомб: 50 МБ (документ) / 5 МБ (текст) / 500 МБ текста на архив; вложенные архивы — только листинг/каталог (глубина 1). docx разбирается как zip+XML (stdlib), xlsx — openpyxl read-only, кривые cp437-имена в zip чинятся попыткой GBK. **Формат определяется по сигнатуре файла, не по расширению** (в папке встречаются rar/7z под именем .zip). **Тяжёлая синхронная часть каждого архива гоняется через `asyncio.to_thread`** — иначе event loop качалки глохнет на часы работы с архивами и Telethon сыплет «Server sent a very old message»/«Security error» (наблюдалось на первом прогоне).
- **PDF и HedEx сканируют папку загрузок рекурсивно** (`os.walk`, скрытые папки пропускаются) — ручная раскладка по подпапкам не прячет файлы от инжеста.
- **Документация HedEx (`KB_HEDEX=1`)** — [kb_hedex.py](kb_hedex.py): `.hdx`-пакеты (zip с DITA-HTML) кладутся в папку загрузок; чанк = страница из `navi.xml` (длинные режутся по ~4000 симв. через `split_text`, заглушки <150 симв. отсекаются), заголовок — `[продукт версия — хлебные крошки]`. Синтетический положительный `chat_id` как у PDF, но `topic_id=1` (конвенция в `ScoredChunk`) — бот показывает «документация: …». **Кросс-версионный дедуп**: sha1 ТЕЛА чанка (без строки заголовка — в ней версия); пакеты обрабатываются от новых версий к старым, общие страницы достаются новейшей (на реальных WLAN-пакетах R023 совпадает с R025 на 87%). Пакет учитывается по MD5 (state `hedex_ingested:<md5>`); существующие хэши тел — `doc_text_hashes()` в [kb_store.py](kb_store.py). Прогон в ночном джобе и бэкфилле, dry-run оценивает объём по размерам HTML в zip без распаковки.
- **Бюджет под контролем**: `kb_backfill.py --dry-run` печатает разбивку стоимости по категориям с учётом флагов; `--max-cost N` останавливает прогон через `BudgetExceeded` ([kb_ingest.py](kb_ingest.py)) — state не двигается, кэш и записанные чанки сохраняются, повторный запуск продолжает без двойной оплаты. Оценки цен — константы в [kb_ingest.py](kb_ingest.py) (`EMBED_PRICE_PER_MTOK`, `VISION_COST_PER_IMAGE`, `WHISPER_PRICE_PER_MIN`).
- **Каталог файлов и прошивок (фаза A, без LLM).** Таблица `files` (ключ — telegram `doc_id`, md5 дозаписывается после скачивания) наполняется тремя путями: живой захват в качалке (**до** фильтра расширений и для чатов `CHAT_IDS ∪ KB_CHAT_IDS` — прошивки каталогизируются без скачивания), ночной инжест и бэкфилл. Разбор имён Huawei — [kb_firmware.py](kb_firmware.py), калиброван по реальному журналу (~1200 имён, покрытие 84% модель+версия): числовые модели (S/CE/AC/CX/AR/MA/AirEngineX…), продукты-слова (iMasterNCE-*, SmartKit, OceanStor-Dorado…), серверные узлы (`1288H V5`, `CH242 V3`), бандлы (`AirEngine 5700&6700&…`, `S200,_S300,…` → модель на каждый номер), точечные версии СХД (`20.1.103.SPC28`), hex-патчи (`SPH1b0`) и hot-патчи (`HP1501`). **Версия ищется первой и вырезается из строки** — иначе жадный хвост модели заглатывает приклеенную версию (`AC6805V200R022…`). В регулярках границы — lookaround, а не `\b` (подчёркивание — словесный символ); длинные словесные префиксы стоят в альтернативе раньше коротких (NE, AR). После расширения регулярок НОВЫЕ семейства подхватываются у старых файлов через `reparse_files` (ночной джоб и бэкфилл, идемпотентно по PK) — он же дозаполняет `files.kind`.
- **Типы файлов** — `classify_name` ([kb_firmware.py](kb_firmware.py)): `signature`/`patch`/`software`/`doc`/`release_notes`/`mib`/`tool`. Подписи (`.asc/.p7s/.cms/.crl`) — почти половина журнала: `find_firmware` их исключает, LLM-матчинг и экстракция тоже.
- **Единый рендер каталога** — `render_grouped` в [kb_render.py](kb_render.py): им пользуются `/fw <модель>`, `/sw` и лист навигации (раньше /fw имел свою плоскую простыню, и фиксы вёрстки расходились). Порядок (решение владельца): 📦 модель (запрошенная — первой!) → софт-часть по веткам от новых к старым (🔀 R025: 💿 образ + 🩹 патчи, затем R024…; «без версии» — последняя; ≤6 веток), а вся документация/RN/MIB/прочее — одним блоком 📖 в конце модели с пометкой ветки у каждой строки (≤8 строк). Дедуп повторных постов по имени; метки «последняя» нет — её заменяет порядок веток. Возвращает `(text, buttons, seen_doc_ids)` — seen нужен /fw для докидывания LLM-кнопок без дублей.
- **Семантика имён Huawei (от владельца)**: `продукт _ Vxxx(ОС: V200=VRP, V600=YunShan) Rxxx(версия системного софта) Cxx(codebase) SPCxxx/SPHxxx(билд софта/патча) . расширение(cc=образ, pat=патч)`. Dash-бандлы `CE6800-8800-9800` — перечень серий (сегменты целиком из цифр); `CE8850-64CQ-EI` — НЕ бандл (буквенные сегменты = суффиксы модели). Подписи ОС — только подтверждённые маппинги в `OS_NAMES`.
- **`/sw <модель>`** — семантическая сводка по веткам системного софта (тот же `render_grouped`, что и /fw, но без LLM-fallback). Поддерживает фильтр ветки: `/sw S5735-S R024`.
- **reparse вычищает пустоверсионные дубли** (`delete_empty_version_rows`): старый парсер не понимал `SPH1b0`/HP и писал связки с `version=''`; после того как разбор имени даёт версию, пустой дубль той же модели удаляется — иначе ветка «без версии» в /sw забита файлами с версиями.
- **`/download <префикс имени>`** — фолбэк, когда парсер бессилен: все скачанные файлы с этим префиксом шлются последовательно (включая `.asc`/`.p7s` — нужны для PGP-проверки; многотомники идут по сортировке имён). Лимит 12 за раз, минимум 8 символов префикса, кулдаун в группе. `files_by_prefix` экранирует LIKE-спецсимволы — в именах Huawei сплошные `_`.
- **Навигация каталога**: `/fw` без аргумента — дерево кнопками «раздел → модель → ветка версий (V600 R025) → файлы с 📎» (callbacks `n:`). Разделы — `product_category` по префиксу модели ([kb_firmware.py](kb_firmware.py), порядок проверок важен: S — последней среди букв, чтобы не съесть SMARTKIT); дерево строится на лету из `fw_all()` (тысячи строк — миллисекунды), листья — `find_firmware_exact`. Ветка группируется по первым 9 символам `version_key` (V+R), но метка кнопки — `version_branch_label` из **сырой** версии (`V600 R025` с нулями как у Huawei; точечные версии СХД `6.1.8` → `6.1`, а не «V6 R1»), не из padded-ключа. Команда `/fw <модель>` работает в группах и личке админа, поиск по подстроке нормализованной модели («5735» → «S5735-L»).
- **LLM-fallback в /fw**: если подстрочный поиск пуст, лёгкая модель матчит запрос к известным моделям каталога И к именам файлов напрямую (`fw_llm_match` в [kb_answer.py](kb_answer.py)) — новые схемы имён и вольные формулировки ловятся без правки регулярок. Выдача помечается «подобрано LLM» (пометка в начале — хвост может резаться лимитом 4096). Качество матчинга приоритетнее стоимости вызова — явное решение владельца.
- **Версия в запросе /fw — фильтр, а не часть модели**: `split_query` ([kb_firmware.py](kb_firmware.py)) отделяет токены `R025`/`V600…`/`SPC…` от модели («S5735-S-V2 R025» → модель `S5735-S-V2`, фильтр `R025`); фильтр применяется и к детерминированной, и к LLM-выдаче. Суффикс `-V2` (поколение железа) — легитимная часть модели: lookahead в MODEL_RE блокирует только версии `V\d+R\d`, а не любые `V\d`.
- **Бэкфилл каталогизирует и чаты качалки вне `KB_CHAT_IDS`** (документы → files/firmware, без инжеста в RAG и без затрат) — иначе файлы, скачанные из «не-KB» чатов, невидимы для `/fw` и кнопок 📎.
- **LLM-экстракция обрабатывает и файлы без подписи** (по одному имени): `files_for_extraction` не требует caption.
- **Каталожное сообщение самоудаляется после 3 успешных отправок по 📎** (`MSG_CLICKS_TO_DELETE`, счётчик в памяти по `(chat_id, msg_id)`): файлы уже в чате, список больше не нужен. Неудачные клики («файла нет на диске») не считаются. Рестарт бота сбрасывает счётчики — приемлемо.
- **`/help` (и `/start`) в группе** — пользовательская справка `_user_help()` (упоминание бота подставляется живым username); в личке админа — та же справка + `ADMIN_HELP_EXTRA`.
- **Кнопка 📎 в /fw шлёт файл с NAS.** Том загрузок смонтирован в kb-bot read-only (`DOWNLOAD_FOLDER`); кнопки появляются только для файлов с заполненным `files.md5` (реально скачаны). Отправка — `send_file` по MTProto (лимит ботов 2 ГБ; 50 МБ — ограничение только Bot HTTP API). **Перед отправкой файл сверяется с каталогом по md5** (`_verify_md5`, хэш в thread'е, кэш по mtime+size): качалка могла перезаписать файл под тем же именем — при расхождении отправка отменяется, админу уходит событие. Переслать оригинал сообщения бот не может: `access_hash` документов у каждого аккаунта свой, а в `files` хранится только `doc_id`.
- **Файлы, скачанные ДО появления каталога, тоже получают md5** — `link_local_files` ([kb_firmware.py](kb_firmware.py)) сопоставляет записи каталога без md5 с журналом `downloaded_files.txt` (парсинг журнала продублирован — импортировать качалку нельзя, side effects). Вызывается ночным джобом и бэкфиллом, идемпотентно. Без этого весь исторический архив был бы без кнопок 📎.
- **Файлы-«сироты» (в журнале и на диске, но без сообщения в чате)** каталогизируются той же `link_local_files`: синтетический **отрицательный** `doc_id` из md5 (telegram-документы всегда положительные), `chat_id=0` — /fw их находит и шлёт по 📎, но ссылки на пост нет. Покрывает удалённые из чата сообщения и файлы, положенные в папку руками.
- **Query expansion при /ask** (`expand_query` + `search_expanded` в [kb_answer.py](kb_answer.py)): лёгкая модель генерирует 2 альтернативные формулировки (разворот сленга + англоязычная терминология Huawei), поиск идёт по всем вариантам, слияние RRF по ключу `(chat_id, msg_first)`. Ошибка расширения не роняет ответ (fallback на исходный вопрос). Это основной рычаг против жаргона — эффективнее смены модели эмбеддингов.
- **Веб-поиск при ответах — `KB_WEB=1`** (только kb-bot): Responses API с tool `web_search` (`answer_with_web`), системный промпт ставит опыт чата выше веба; веб-URL из annotations — отдельным блоком 🌐. Любая ошибка веб-пути — тихий fallback на обычный chat.completions. При пустой базе и включённом вебе бот всё равно отвечает из веба, но `found=False` (петля gaps работает от базы, не от веба).
- **Источники под ответом — только процитированные.** LLM получает top-8 фрагментов, в «Источники:» попадают лишь `[n]`, упомянутые в тексте ответа (regex по `\[(\d+)\]`); если LLM не сослался ни разу — топ-3. Раньше список резался до 5 и ссылки `[6+]` повисали.
- **Бот отвечает только там, где его ждут.** `_parse_chat_topics` ([kb_bot.py](kb_bot.py)) разбирает `KB_ANSWER_CHAT_IDS` в `{чат: {топики}}`, пустое множество = весь чат; `_topic_allowed` проверяет входящее через `message_topic_id` из [kb_ingest.py](kb_ingest.py). Гейт стоит ОДИН раз в групповом обработчике — под него автоматически попадают и вопросы, и `/fw`/`/sw`/`/download` с отправкой файлов. В форуме без этого бот засоряет все топики.
- **Закрытый топик = топик, где бота не ждут.** `_topic_allowed` спрашивает `_closed_in` — кэш `{чат: (когда протухнет, закрытые топики)}` на `TOPIC_CACHE_TTL`=10 мин поверх `fetch_topics` ([kb_ingest.py](kb_ingest.py), возвращает `{id: (заголовок, закрыт ли)}`; `fetch_topic_names` — обёртка над ним). Спрашивать статусы на каждое сообщение нельзя: лишний RPC и повод для флуд-лимита, а закрывают топики редко. Пустой ответ (обычная группа; боту метод могут и не дать) кэшируется тоже — иначе неудачный запрос повторялся бы на каждое сообщение, — и тогда всё ловится вторым слоем.
- **Второй слой — тихий отказ на отправке.** `_reply` (через него ходят `_reply_temp` и ответы) ловит `_is_mute_error`: явные классы (`ChatWriteForbiddenError`, `TopicDeletedError`, `ChatAdminRequiredError`, `UserBannedInChannelError`) плюс `RPCError` с `TOPIC_CLOSED`/`TOPIC_DELETED` в `message` — своего класса у `TOPIC_CLOSED` в telethon 1.44 НЕТ, прилетает generic `BadRequestError`. Вместо трейсбека — строка в лог, `None` вместо сообщения и запись топика в тот же кэш (следующее сообщение отсечёт уже гейт). Прочие ошибки отправки пробрасываются как раньше. Затронуты все пути записи в группу: ответ на вопрос (в `qa_log` останется запись без `answer_msg_id` — логируется отдельным warning, чтобы расход в `/status` был объясним), пачка `/download` (обрывается целиком), кнопка 📎 (всплывашка «топик закрыт»), авто-ответ петли gaps (пробел закрывается — иначе каждую ночь платим за ответ, который некуда доставить) и еженедельный пост gaps (событие админу, вопросы НЕ помечаются опубликованными).
- **Уборка за собой** (`KB_CLEANUP_MINUTES`>0): служебные ответы (каталожные простыни, подсказки, «подожди») и сама команда пользователя удаляются через N минут — `_reply_temp` ставит их в очередь `_cleanup`, `cleanup_loop` раз в 30 с удаляет. Ответы на вопросы НЕ трогаются (это знание), личка админа тоже. Очередь в памяти: после рестарта хвост остаётся — как и со счётчиками кликов. Удаление чужого сообщения требует прав админа у бота; нет прав — молча пропускаем.
- **`/sources` — инвентарь базы** (`sources_report` в [kb_store.py](kb_store.py) + `render_sources` в [kb_render.py](kb_render.py)): что именно проиндексировано — чаты с периодом, пакеты HedEx, PDF и текст из архивов, плюс счётчики обработанного по state. Виды источников различаются конвенцией chat_id/topic_id (чат <0; HedEx >0 и topic_id=1; PDF и архивы >0 и topic_id=0), поэтому отчёт строится одним запросом без отдельной таблицы. Доступна и в группе, и в личке админа (в личке — длиннее список).
- **Оценки ответов**: кнопки 👍/👎 (`Button.inline` + `events.CallbackQuery`), лог в `qa_log`, 👎 → событие `feedback` админу. Вопросы с `found=0` или `rating<0` — команда `/gaps` (карта дыр в базе).
- **Диалоги: реплай на ответ бота = follow-up** (без /ask и упоминания). `qa_log.answer_msg_id` фиксируется после отправки ответа (в т.ч. авто-ответов gaps); входящий реплай ищется по `qa_by_answer_msg`, цепочка Q&A (`qa_dialog`, ≤3 обменов через `parent_qa_id`) уходит в промпт отдельным блоком И в поиск доп. вариантами (`_search_expanded(extra=...)` — follow-up «а на R024?» сам сущностей не несёт, их держат предыдущие вопросы). Работает в группе, личке админа и на авто-ответах петли gaps; кулдаун действует.
- **Петля gaps замыкается сама** (`gaps_loop` в kb_bot, тик раз в час, сделанность — в state): через час после `INGEST_HOUR` бот повторно отвечает на вопросы с `found=0` реплаем на исходное сообщение (`qa_log.msg_id`) — обсуждение из чата уже проинжещено. 👎-вопросы автоматом НЕ ретраятся (повторный плохой ответ хуже молчания). Еженедельный пост «помогите сообществу» — пн 10:00 в `KB_GAPS_CHAT_ID`/`KB_GAPS_TOPIC_ID` (пусто = выключен), каждый вопрос постится один раз (`gap_posted`).
- **Фаза B каталога — LLM-экстракция** ([kb_extract.py](kb_extract.py)): ночью подписи файлов без связок → `firmware` с `confidence='medium'`, `source='caption'`; таксономия серий → таблица `devices` (`kind: model|series`, `parent`). Ошибки LLM НЕ помечают файл обработанным (`llm_done`) — ретрай завтра. Картинки помечаются без вызова LLM. `find_firmware` разворачивает серии в обе стороны: запрос-модель видит прошивки своей серии (`is_series=1`), запрос-серия — прошивки моделей. Миграции схемы — блок `ALTER TABLE` в `_init_schema` с подавлением `OperationalError`.
- **Очередь `/review` не растёт бесконечно (авто-review).** Три уровня разгрузки, все идемпотентны и гоняются в ночном джобе/бэкфилле после reparse: (1) `auto_resolve_firmware` снимает medium-связки, чью модель независимо подтвердил детерминированный разбор имени того же файла (высокая-запись из `reparse_files` их уже представляет) — вычищает исторический хвост, накопленный, пока парсер был слабый; (2) серии авто-подтверждаются при создании (`build_series` → `confirmed=1`) и разом `confirm_all_series()` — таксономия низкорисковая, неверную серию видно при навигации; (3) остаток LLM-догадок — кнопка «✅ Принять все N» в `/review`: двухшаговая — сперва превью подтверждаемого списка (callback `c:allfw`), затем подтверждение (`c:allfw2` → `confirm_all_firmware`) или `c:cancel`. Поштучные `c:f:`/`c:d:` тоже остались; callback только для `KB_ADMIN_IDS`.
- **Админ-канал через очередь `events` в базе.** Качалка пишет события (скачивания, инжест, ошибки — через `_kb_event()`, ошибки KB не ломают скачивание), kb-bot раз в минуту рассылает непрочитанные админам из `KB_ADMIN_IDS` в личку. События помечаются доставленными только после успешной отправки; при `/notify off` копятся и видны через `/events`. Личка не-админов игнорируется; любой текст админа в личке без команды — вопрос к RAG. Бот не может написать первым: админ должен один раз нажать Start.
- **`events_cost` в `/status` уже включает медиа-затраты** инжест-прогонов — `media_cost` из `media_cache` это деталь, а не слагаемое (иначе двойной счёт).
- **Ночной джоб** — `kb_ingest_loop()` в качалке ([librarian.py](librarian.py)): тик раз в минуту, срабатывает в `INGEST_HOUR` локального времени (сделанность суток — state `ingest_done_date`; tzdata ставится в Dockerfile ради `TZ`) **или по запросу админа** — `/ingest` (и кнопка в `/status`) ставит state `ingest_request`, качалка подхватывает в течение минуты. Цикл: инжест чатов → пост-инжест конвейер из [kb_pipeline.py](kb_pipeline.py).
- **Пост-инжест конвейер — ЕДИНСТВЕННОЕ место порядка шагов** ([kb_pipeline.py](kb_pipeline.py), `run_post_ingest`): каталог (link/reparse/auto-resolve/серии) → PDF → архивы → HedEx → LLM-экстракция → бэкап через `VACUUM INTO` (горячее копирование файла с WAL небезопасно), не чаще раза в `KB_BACKUP_DAYS` дней (по умолчанию 7; копия весит как сама база — при 185 тыс. чанков это 2.1 ГБ, а потеря базы некритична: она пересобирается из Telegram и файлов тома). Его зовут ночной джоб (`report='events'` — логи + события админу) и бэкфилл, включая `--local-only` (`report='print'`). Шаги изолированы: ошибка одного не роняет остальные; `BudgetExceeded` останавливает конвейер, state обработанного уже зафиксирован. Новую стадию добавлять СЮДА, а не в вызывающих.
- **MD5 файлов кэшируется по (размер, mtime)** — `store.cached_md5`/`remember_md5`, обёртка `kb_store.file_md5` ([kb_store.py](kb_store.py)). Без кэша каждый прогон перечитывал все `.hdx`/PDF/архивы целиком только ради проверки «не обработано ли уже» (у владельца это ~8 ГБ за ночь): минуты IO и, главное, вымывание базы из кэша страниц — после этого холодный поиск занимал 8 с вместо 0.6 с. В async-коде (kb_archive) кэш проверяется в основном потоке, а само хэширование уходит в `asyncio.to_thread`.
- **Прогресс длинных шагов виден снаружи**: `run_post_ingest` пишет текущий шаг в state `pipeline_status` (и чистит его в конце), ночной джоб передаёт колбэк, который троттлингом раз в 20 с логирует и обновляет тот же ключ; `/status` в личке показывает строкой «⏳ Сейчас идёт: …». Шаги архивов и HedEx идут часами — без этого снаружи выглядело, будто ничего не происходит.
- **Оплаченный результат vision/whisper не теряется на блокировке базы**: `remember_media` ([kb_ingest.py](kb_ingest.py)) повторяет запись в `media_cache` (5 попыток с паузой), а `busy_timeout` базы — 30 с. Раньше при работающем ночном конвейере (шаги архивов/HedEx держат длинные транзакции) соседний писатель ловил «database is locked», описание картинки выбрасывалось уже ПОСЛЕ оплаты, и повторный прогон платил снова. Окончательный отказ пишется в лог отдельной строкой — потеря должна быть видна.
- **Бэкфилл** (`kb_backfill.py`) запускать только при остановленной качалке (общая сессия!) и **до** включения ночного инжеста:
  `docker compose stop librarian` → `docker compose run --rm librarian python kb_backfill.py --dry-run` (оценка объёма/стоимости) → без `--dry-run` → `docker compose start librarian`.
- **kb-bot не падает без конфига**: без `KB_BOT_TOKEN`/`KB_ANSWER_CHAT_IDS` уходит в вечный sleep с ошибкой в логе (чтобы не крутить crash-loop под `restart: unless-stopped`). Для упоминаний боту нужен выключенный privacy mode (`/setprivacy` → Disable в BotFather).
- **Запросы FTS санитизируются** (`search` в [kb_store.py](kb_store.py)) — сырой пользовательский текст в `MATCH` роняет FTS5-синтаксис.
- **Для моделей класса gpt-5 не передавать `temperature`/`max_tokens`** (`answer_question` в [kb_answer.py](kb_answer.py)).
- **Чанк не может быть длиннее лимита эмбеддера — два слоя защиты.** (1) `split_text` ([kb_hedex.py](kb_hedex.py), используется также [kb_archive.py](kb_archive.py)) рубит и сверхдлинную ОДИНОЧНУЮ строку: в DITA-HTML переносов может не быть вовсе (широкая таблица в один `<tr>`), и прежняя версия клала такую строку в чанк целиком — 28 тыс. символов уезжали в эмбеддер, DeepInfra отвечал HTTP 400 «8193 > 8192 токенов» и ронял весь шаг конвейера (прод, 09.2026). (2) `EMBED_MAX_CHARS`=8000 в [kb_ingest.py](kb_ingest.py) — потолок ОДНОГО входа эмбеддера (было 20000 ≈ 10500 токенов на техдокументации при ~1.9 симв./токен). Второй слой прикрывает пути, где резать нельзя: id чанка выводится из номеров сообщений/страниц (`sha1(chat_id:msg_first:msg_last)`), поэтому части одной страницы PDF или одного сообщения с длинной расшифровкой схлопнулись бы в один id — там текст в базе остаётся целиком (нужен LLM как контекст), а обрезается только то, что уходит в эмбеддер.
- **Бинарная квантизация векторов исследована и ОТЛОЖЕНА (09.2026) — не переделывать без нужды.** Замеры на реальных данных: (1) ранжирование ЧИСТО по битам теряет ~17% MRR (0.527→0.437 обычные, 0.476→0.397 сленг) — неприемлемо; (2) биты + переранжирование точными векторами дают качество, идентичное полному скану (MRR совпадает до третьего знака уже при пуле 100–200); (3) НО случайное чтение векторов из vec0-таблицы стоит ~0.85 мс за вектор — дороже полного скана, поэтому наивная схема «bit-таблица + rerank из chunks_vec» получилась в 20 раз МЕДЛЕННЕЕ (446 мс против 23 мс). Рабочая схема требует хранить точные вектора в ОБЫЧНОЙ таблице (B-tree даёт быстрый доступ по rowid) плюс numpy для переранжирования: 6.6 мс против 22.9 мс на 6.6 тыс. чанков при полностью совпадающей выдаче. Отложено осознанно: апгрейд NAS до 10 ГБ RAM держит базу в кэше страниц, а тёплый поиск 0.58 с на 185 тыс. чанков незаметен на фоне 5–15 с генерации ответа. Возвращаться, когда база перестанет помещаться в кэш (~500 тыс. чанков, файл >5 ГБ): тогда холодный поиск снова упрётся в 7.9 с полного скана 758 МБ векторов.
- **Смена модели эмбеддингов — только через [kb_reembed.py](kb_reembed.py)** (оба сервиса остановить; Telegram не нужен — тексты в базе). Вектора разных моделей несравнимы даже при равной размерности; guard `check_embed_cfg` ([kb_ingest.py](kb_ingest.py), state `embed_cfg`) блокирует инжест (событие админу) и ответы бота, если env разошёлся с базой. `reset_vectors` пересоздаёт `chunks_vec` под новую размерность; state обновляется только после успешного прогона.
- **Эмбеддинги можно вынести на сторонний OpenAI-совместимый провайдер** (`EMBED_API_BASE`+`EMBED_API_KEY`, тот же `openai`-клиент с другим base_url): `embed_client()` в [kb_ingest.py](kb_ingest.py) — единственная точка выбора; ответы/vision/whisper всегда идут через `openai_client()` (OpenAI). При кастомном base параметр `dimensions` НЕ передаётся (Matryoshka — фича OpenAI), размерность ответа сверяется с `EMBED_DIM` (fail-fast до записи в базу). Все вектора нормализуются в `embed_texts` — KNN sqlite-vec ранжирует по L2, что совпадает с косинусом только на единичных векторах (OpenAI нормализует сам, сторонние — не факт).
- **Отказ эмбеддинг-провайдера не роняет бота**: `search_expanded` ловит ошибку и ищет FTS-only (`store.search(..., query_vector=None)`) — фолбэк на другую эмбеддинг-модель невозможен в принципе (несравнимость векторов).
- **Рекомендация владельцу (бенчмарк [kb_bench.py](kb_bench.py) на реальном корпусе, 300 вопросов, 07.2026)**: `BAAI/bge-m3` через DeepInfra (`EMBED_API_BASE=https://api.deepinfra.com/v1/openai`, `EMBED_DIM=1024`) — MRR@10 0.527/0.476 (обычные/сленг) против 0.442/0.412 у прод-`text-embedding-3-large@1024`, цена $0.01/1M ток. (в 13 раз дешевле). Полная размерность large (3072) даёт лишь +0.01 MRR — потолок OpenAI ниже всех локальных моделей бенча. Кэши бенча — `fromChat/bench_cache/` (вопросы + .npy), гоняется локально на GPU (не на NAS).

## Пространства знаний (мультипродуктовость)

- **Пространство — область знаний целиком**: свои чаты-источники, свои чаты
  ответа, своя папка документов, своя персона в промпте, свои подсказки
  терминологии, свой чат для еженедельного поста gaps. У чанка ровно одно
  пространство происхождения (`chunks.space`), у вопроса — область поиска.
  Проектный документ с обоснованиями — [SPACES_PLAN.md](SPACES_PLAN.md).
- **Конфиг — `spaces.toml`** ([пример](spaces.toml.example), stdlib `tomllib`,
  путь в `KB_SPACES_FILE`, монтируется в оба контейнера). **Файла нет, он
  пуст или на его месте каталог (docker так делает для несуществующего
  bind-mount) — собирается ОДНО неявное пространство из env**
  (`KB_CHAT_IDS`/`KB_ANSWER_CHAT_IDS`/`CHAT_IDS`/`FILE_EXTENSIONS`/
  `DOWNLOAD_FOLDER`/`KB_GAPS_*`, slug из `KB_SPACE`, по умолчанию `main`),
  и поведение одиночной установки не меняется ни в чём. `redeploy.sh`
  создаёт пустой `spaces.toml`, чтобы docker не сделал на его месте папку.
- **`answer` различает «не задано» и «пусто»**: ключа нет — бот отвечает во
  всех чатах-источниках области (обычный случай, это одни и те же чаты);
  `answer = []` — не отвечает нигде, режим «только копим знания» для
  больших публичных чатов. Спрашивать про такую область можно из любого
  своего чата указателем `#slug`.
- **Переезд с .env на файл — `kb_spaces.py --dump > spaces.toml`**: печатает
  текущую конфигурацию (в т.ч. собранную из env) готовым TOML. Переписывать
  её руками — способ молча потерять топик ответа или расширение качалки;
  селфтест проверяет, что дамп читается обратно без потерь.
- **Id чатов и топиков — `kb_chats.py`** (при остановленной качалке: общая
  сессия): список диалогов аккаунта с id и типом, `--topics <chat_id>` —
  топики форума с пометкой закрытых. Ничего не меняет, только читает.
- **Первая секция конфига — пространство по умолчанию.** В него попадает
  всё без явной метки и всё, что было в базе до появления пространств.
  Переименование после запуска = потеря привязки старых данных.
- **`kb_spaces.py` — единственное место**, где конфиг превращается в
  объекты, chat_id — в домашнее пространство, а текст «#b4 вопрос» — в
  область поиска. Остальные модули знают только slug. `Spaces.resolve()`
  возвращает `Scope` (где искать, можно ли расширяться, как подписать
  ответ) — обработчики бота этих правил не знают.
- **Область поиска**: указатель `#b4`/`#all` в тексте важнее всего (и
  отключает фолбэк — человек сказал, где искать); иначе домашнее
  пространство чата с авто-фолбэком на все области; чат без привязки
  (личка админа) ищет везде сразу. `default_scope='all'` у пространства
  делает его чаты сразу глобальными. Хэштег, а не `/ask@b4`: последнее
  Telegram трактует как адресацию другому боту.
- **В одиночной установке `resolve` всегда отдаёт единственное
  пространство** (даже на `#all` и в личке): глобальный поиск и поиск «в
  своём» там совпадают, но скан одного раздела vec0 дешевле полного.
- **Пометка области — строкой в НАЧАЛЕ ответа** (`_scope_note` в
  [kb_answer.py](kb_answer.py)): 🔀 при фолбэке, 🎯 при явном указателе.
  Хвост режется лимитом 4096, поэтому не в конце. При одном пространстве
  пометок нет вовсе — объяснять нечего.
- **Персона и подсказки — из конфига пространства**: `persona` идёт в
  системный промпт («ассистент telegram-чата <persona>»), `hints` — в
  расширение запроса (разворот сленга в терминологию своей области). При
  глобальном поиске персона общая, а каждый фрагмент контекста помечен
  областью — иначе модель молча смешает Huawei с B4.
- **Скорость — partition key sqlite-vec**: `vec0(space TEXT PARTITION KEY,
  embedding float[N])`, KNN по своей области сканирует только её строки
  (замер на трёх пространствах — в 2.6 раза быстрее полного). FTS5 получил
  колонку `space UNINDEXED` и фильтр в том же запросе. `INSERT OR REPLACE`
  в vec0 с partition key НЕ работает («UNIQUE constraint failed») —
  `set_vector` делает DELETE + INSERT.
- **Миграция базы — [kb_spaces_migrate.py](kb_spaces_migrate.py)**, разово
  при остановленных сервисах: метит существующие строки и перекладывает
  векторы в новую таблицу как есть, без переэмбеддинга (ни Telegram, ни
  OpenAI). Замер на копии прода: 6617 чанков за 22 с, векторы побайтово те
  же, выдача поиска совпала; на 185 тыс. — порядка 10–30 минут, нужно ~3 ГБ
  свободного места (бэкап `.pre-spaces` весит как база + файл временно
  растёт). **Хранилище отказывается открывать немигрированную базу с
  данными** — иначе поиск по пространству молча стал бы глобальным.
- **Имя области по умолчанию зафиксировано в базе** (state `spaces_default`):
  на старте хранилище сверяет его с первой секцией конфига и при
  расхождении НЕ поднимается. Классическая ловушка — мигрировать базу как
  «main», а потом завести `spaces.toml` с первой секцией `[huawei]`: поиск
  по своей области возвращал бы пустоту при живых данных. Чинится
  `kb_spaces_migrate.py --rename-space main huawei` (при остановленных
  сервисах): переименовывает строки, ключи state документов и разделы vec0.
- **Ключи state документов**: `store.doc_key()` даёт исторический вид
  `pdf_ingested:<md5>` для пространства по умолчанию и
  `pdf_ingested:<space>:<md5>` для остальных. Иначе весь обработанный
  корпус выглядел бы новым и был бы переиндексирован за деньги; а один и
  тот же файл в папках двух пространств должен инжеститься в оба.
- **Этап медиа бэкфилла идёт пулом** (`KB_MEDIA_CONCURRENCY`, по умолчанию 4): узкое место — не сеть Telegram (картинка приходит за доли секунды), а ожидание vision — последовательно выходило ~20 с на изображение, и большой чат обрабатывался бы сутки. Очередь ограничена `concurrency * 2`, поэтому в памяти живёт несколько картинок, а не история чата. Бюджет проверяется после каждого ответа, так что перебор возможен на размер пула (~$0.02). Упавший запрос не убивает рабочего — иначе очередь переполнится и продюсер встанет навсегда. Инжест-путь (`ingest_chat`) остался последовательным: ночная дельта мала, а к этапу [3/3] всё уже в кэше.
- **Обогащение медиа — свойство пространства** (`vision`/`voice` в секции: не задано — как `KB_VISION`/`KB_VOICE` в env, `true`/`false` — переопределение). Решает `media_policy` → `MediaPolicy` ([kb_ingest.py](kb_ingest.py)), объект протянут в `ingest_chat`/`enrich_chat_media`/`enrich_message` вместо чтения глобального флага из недр. Иначе выключение vision ради бэкфилла чужого чата выключало его и своему, а обратное включение заставляло ночной инжест платить $0.004 за каждый чужой скриншот. `--dry-run` считает бюджет по политике каждой области.
- **Каталог прошивок — свойство пространства** (`catalog = "huawei"|"none"`):
  регулярки имён Huawei на чужих файлах дали бы ложные связки. У B4 и Telemt
  прошивок нет вообще — ни `folder`, ни `download`, только чаты (решение
  владельца). Шаги каталога и LLM-экстракции в конвейере запускаются, только
  если есть хоть одно пространство с каталогом.
- **Журнал дедупликации качалки — на папку** (`downloaded_files.txt` внутри
  `folder`): файл с тем же именем в другом пространстве — другой файл.
- **Пост-инжест конвейер идёт по пространствам** ([kb_pipeline.py](kb_pipeline.py)):
  документные шаги — по папке каждого, с меткой; бэкап один на базу.
  Бэкфилл умеет `--space b4` — завести новую область, не трогая остальные.
- **Селфтест мультирежима — `python kb_spaces_check.py`** (отдельный файл:
  librarian и kb_store читают окружение на импорте, поэтому spaces.toml
  задаётся ДО импортов). Ловит «всё уехало в одно пространство»: чанки без
  метки, общий журнал скачиваний, общий ключ state у одноимённых файлов в
  разных папках, глобальный поиск вместо своей области.

## Устойчивость к сетевым сбоям

- **Внутренние реконнекты Telethon** — `connection_retries=-1`, `retry_delay=300`, `auto_reconnect=True` (конструктор `TelegramClient` в [librarian.py](librarian.py)). Telethon бесконечно пытается восстановить разорванную сессию, выжидая 5 минут между попытками — короткий ретрай при кратковременном разрыве сети бесполезен и только засоряет журнал.
- **Внешний exponential backoff** — `run()` оборачивает `client.start()` + `run_until_disconnected()` в цикл с задержкой 300 → 600 → 1200 → 1800 секунд ([librarian.py](librarian.py)). Тот же паттерн — в `kb_bot.py`. Backoff сбрасывается до 300 после успешного коннекта.
- **Опциональный MTProto-прокси** — `MTPROXY_HOST/PORT/SECRET` в `.env`, применяется ко всем трём клиентам через [tg_conn.py](tg_conn.py) (`proxy_kwargs()`). Секрет только hex или `dd`+hex: FakeTLS (`ee…`) Telethon не поддерживает — такой секрет игнорируется с warning, соединение идёт напрямую (сознательно: лучше работать напрямую, чем не работать вовсе).
- **Подавление логов Telethon до WARNING** (`logging.basicConfig` в [librarian.py](librarian.py)). Без этого журналы NAS забивались сообщениями вида `Got difference for channel X updates`, `Closing current connection`, `Attempt N at connecting failed`. Остаются только реальные предупреждения.
- **Авто-перезапуск контейнеров** — `restart: unless-stopped` у обоих сервисов поднимает контейнер, если процесс всё-таки упадёт (OOM, segfault, исчерпание backoff).
- **Ограничение логов Docker** — `json-file` драйвер с `max-size: 10m` × `max-file: 3` у обоих сервисов ([docker-compose.yml:29-33](docker-compose.yml#L29-L33)). Без этого `/var/lib/docker/containers/<id>/<id>-json.log` рос бы бесконечно.
